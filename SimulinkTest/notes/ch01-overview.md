## 1. 本章目标
- 理解 Simulink Test 解决什么问题、适合哪些测试场景。
- 掌握工具箱的完整工作流（编写 → 管理 → 执行 → 报告 → 自动化）。
- 建立"Test File / Test Suite / Test Case / Iteration"的核心对象心智模型。
- 了解三种测试类型与四种测试模式，以及配套工具箱的职责划分。

## 2. 核心概念

### 2.1 Simulink Test 是什么
针对**模型、生成代码、以及仿真或物理硬件**编写、管理和执行基于仿真的**系统性测试**。
关键价值：把"靠人眼看波形"变成"可重复、可断言、可覆盖、可追溯、可自动化的质量保障"。

### 2.2 典型应用场景
| 场景         | 说明                                         |
| ---------- | ------------------------------------------ |
| 单元测试       | 用 Test Harness 隔离单个子系统/模块，单独验证             |
| 回归测试       | 改完模型后自动重跑历史用例，确认旧功能未破坏                     |
| 功能测试       | 对输入/输出关系做逻辑断言                              |
| 背靠背测试(等效性) | 模型仿真 vs 生成代码(SIL/PIL)数值对比，验证代码与模型等价        |
| 覆盖率分析      | 用量化指标评估测试完整性 (Simulink Coverage)           |
| 需求追溯       | 把测试用例链接到需求，满足功能安全管理 (Requirements Toolbox) |

### 2.3 测试循环（Test File 中的"运行/捕捉"模型）
Simulink Test 采用 **WR（Write / Run）模式**：先**运行(捕捉)**模型采集数据，再**编写**测试用例去比较/评估。

### 2.4 三种测试模式（区别、用途）
| 模式 | 作用 | 典型用途 |
|------|------|----------|
| 模型在环 (MIL) | 在 Simulink 中直接对模型仿真 | 开发早期、单元/功能测试 |
| 软件在环 (SIL) | 运行从模型生成的**代码** | 验证生成代码与模型一致 |
| 处理器在环 (PIL) | 在目标处理器上运行生成代码 | 验证嵌入式环境下的行为 |
| 硬件在环 (HIL) | 在真实硬件/被控对象环上实时运行 (Simulink Real-Time) | 系统级实时验证 |

### 2.5 测试对象层次结构（核心心智模型）
```
Test File  (.mldatx)      ← 最顶层容器，可含覆盖率、报告设置
 └─ Test Suite            ← 中间层，给 Test Case 分组
     └─ Test Case         ← 测试执行的最小单元
         └─ Test Iteration ← 同一 Test Case 的参数/输入变化（可有多个）
```
- 一个 Test File 可含多个 Suite；一个 Suite 多个 Case；一个 Case 多个 Iteration。
- 结果层级严格对应：FileResult > SuiteResult > CaseResult > IterationResult。

### 2.6 三种测试模板 / 比较准则
- **仿真测试（Simulation）**：能跑通 + 满足模型内断言/评估即可，最轻量。
- **基线测试（Baseline）**：把仿真输出与"期望数据集（基线）"比较，用于功能/回归测试。
- **等效性测试（Equivalence）**：比较**两次仿真**的输出（如 MIL vs SIL），用于背靠背验证。
- 比较结果可选 → 结果报告：Simulink Test 自身；覆盖率报告：Simulink Coverage。

### 2.7 关键组件模块（后续章节逐个展开）
| 组件 | 作用 |
|------|------|
| **Test Manager**（App） | 编写、组织、执行、分析测试与结果的主界面 |
| **Test Harness**（测试框架） | 隔离被测对象、提供输入/输出的专用仿真环境，不侵入主模型 |
| **Test Sequence**（测试序列模块） | 用步骤/转移构造按时间或逻辑行进的输入，可编程 |
| **Test Assessment**（测试评估模块） | 对被测对象行为做验证（verify 语句），判断通过/失败 |
| **Observer Reference / Port** | 无线访问模型任意信号，不改端口/接口即可取值 |
| **sltest.* API** | 命令行/脚本编程接口，用于自动化 |

### 2.8 数据来源（测试输入）
- Signal Editor（图形化）
- Excel / MAT 文件 / m 脚本（外部数据）
- Test Sequence 模块（时间/逻辑驱动的步骤序列）
- Simulink Design Verifier（自动生成，扩大覆盖率/复现错误）

### 2.9 评估方式（判断通过/失败）
1. verify / assert 语句（Test Assessment / Test Sequence / Stateflow 图内）
2. 逻辑与**时序评估**（时间窗口、事件次序）
3. 容差比较（基线/等效性的值与时间容差）
4. 自定义准则脚本（MATLAB）

## 3. 关键工作流（一句话流程）
> 准备测试计划 → 为被测组件建 Test Harness → 编写输入与评估 → 放进 Test File/Suite/Case → 运行 → 查看结果与覆盖率 → 生成报告 → （可编程/CI 自动化）

## 4. 语法 / API 速查（本章）
- 打开测试管理器：`sltest.testmanager.view`
- 文件扩展名：`.mldatx`（测试文件）、`.mltbx`（非）、harness 存档 `.slx`/外部文件
- 内置示例在本机打开：在 MATLAB 命令行执行 `openExample('simulinktest/BaselineTestExample')` 等

## 5. 常见误区与提示
- **不要**在主模型里到处加测试用的端口/模块；用 Test Harness 与 Observer 保持主模型"干净"。
- "仿真测试能跑通 ≠ 功能正确"，功能正确要靠评估/断言/比较。
- SIL/PIL 子系统不支持覆盖率分析（文档注明）。
- 覆盖率需要另装 Simulink Coverage，需求追溯需要 Requirements Toolbox。

## 7. 问答记录
（学习过程中记到这里）

### Q1：Test Harness（测试框架）到底是什么？
你右键组件后点"测试框架 > 为 'xxx' 创建"，得到的就是 Test Harness，但准确说：
- **Test Harness 是一个独立的小模型（块图）**，它把"在测组件"复制/链接进去并"隔离"出来，再给它配上**输入源、输出汇和验证模块**，从而形成"只针对这个组件"的测试环境。
- 它**不是**主模型的一部分，而是与主模型**关联**的单独模型：拥有独立模型工作区（workspace）和独立配置集（configuration set）。改 harness 里的被测组件，主模型会同步更新（默认打开时同步）。
- 用途：单元测试隔离子系统、闭环测试（把被控对象模型加进 harness）、避免把验证模块堆进主模型等。
- 用 API 创建：`sltest.harness.create` 或测试管理器里的"为模型组件创建测试"向导。
> 官方定义页：`gs/create-a-test-harness.html` 与 `ug/relationship-between-harness-and-model-block-diagrams.html`。

### Q2：面板里的两个"Test Sequence"是什么？
创建 Test Harness 的"信源和信宿"对话框里，会遇到两个带 TestSequence 的选项，含义不同：
1. **信源 = Test Sequence**：把 harness 的**输入**交给一个 Test Sequence 模块来生成——它不是静态的常量/波形，而是"按时间步进、按逻辑转移"的**编程式输入序列**。适合做复杂的、动态的激励。
2. **使用以下项生成函数调用信号 = Test Sequence**：这是**调度/驱动**选项——用 Test Sequence 模块**在仿真中触发（调用）函数调用子系统或函数**，相当于"测试骨架/调度器"。它针对的是"函数调用"类型的在测组件。
简单记：**第一种 = 用 TestSequence 当输入源；第二种 = 用 TestSequence 当函数调用发生器/调度器。** 详见官方 `gs/create-a-test-harness.html` 与"使用 Stateflow 图进行测试框架输入和调度"章节。
> 注：Test Sequence 底层基于 Stateflow，你可把它理解为"测试专用的小状态机/时序脚本"。

### Q3：基线测试
基线测试你说是把仿真输出与"期望数据集（基线）"比较，用于功能/回归测试，这个基线是怎么来的呢，是我自己设置一个参考值还是我跑一组值设为基线

**答：基线主要是"跑出来并捕捉"的，不是手填的。** 分两种来源：
1. **最常用——捕捉（Capture）**：在 Test Manager 的"基线准则"区点"捕获"，让模型用当时给定的输入真正仿真一遍，把输出信号**保存成基线数据集**（如 `baseline_data`）。之后每次运行测试，**当前的仿真输出**会去和这份"当初捕捉的标准输出"对比。→ 官方教程 `gs/create-a-simple-baseline-test.html` 就是这个流程。
2. **也可以 external（从文件来）**：如果你已有一份可信的期望数据（实测数据、历史数据、手写/算出的参考值），可以用 MAT/Excel 等文件作为基线数据集指定给测试用例。

> 一句话：默认做法 = **先跑一组/一版自认为正确的输出，捕捉下来当"标准答案"**，以后每次改完模型重跑，输出偏离这份基线就报警。这也正是"回归测试"的机制。

### Q4：等效性测试
这是三种基本类型测试的一种，核心就是比较两次仿真的输出，对吧，那除了模型 VS 生成代码的背靠背测试属于等效性测试外，我把模型修改了后比较结果是不是也是属于等效性测试。

**答：核心机制对——等效性测试就是比较"两次仿真"的输出。** 但"改模型前后对比"官方**不归入等效性测试**，而是用**基线测试**来做。区别在于"比较对象"是谁：
- **基线测试**：当前仿真 vs **一份固定的期望数据集（基线）**。改模型前后回归 = 同一模型新版本输出 vs 之前捕捉的旧基线。→ 你的"改模型后比较"场景，**官方推荐用基线测试**。
- **等效性测试**：**两个并行的仿真**互相对比，讲究"两者地位对等、同一时刻都在跑"。典型：
  - **背靠背（back-to-back）**：模型仿真 vs **生成代码**（MIL vs SIL/PIL/HIL）；
  - 同一组件在**不同 MATLAB 版本 / 不同仿真环境**下跑，验证等价；
  - 两个**不同实现**（如重构前后两个独立模型）验证行为一致。
> 官方定义（`ug/test-two-simulations-for-equivalence.html`）："测试管理器中的等效性测试用例比较**两个仿真**之间的信号输出以确定等效性。……（例）设置了来自主模型和测试框架的信号以供记录。记录的信号用作**普通模式和 SIL 模式**之间的等效性准则。"
> 所以"模型 vs 生成代码"是等效性测试最典型的应用；而"我改了模型、想对比新旧行为"通常用基线测试更贴切（基准是固定的）——等效性测试也可以实现，但它的"两人对赛"形态主要是为"不同执行环境/实现"设计的，不是为回归看板设计的。

### Q5：回归测试是不是独立于你说的三种常见测试类型？
**答：不是平级的第四种"测试类型"，而是一种"测试目的/策略"，工具上主要落在基线测试里实现。** 要把两层概念分开：
- **三种常见测试类型 = "用什么判据去判断"**（机制/判据维度）：仿真、基线、等效性。它们回答的是"怎么判定通过"。
- **回归测试 = "测试要达到什么目的"**（目的/场景维度）：确保**改动没有破坏已存在功能**。它回答的是"这次测是为了防回归"。

回归测试**没有自己专属的判据模板**，而是"复用上面类型"去达成目的：
- 回归测试**最常用基线测试**：把改动前捕捉的输出当基线，改动后跑一遍，输出不变 → 没破坏旧功能。
- 若回归的是"两个实现/环境"的一致性，也可用等效性测试。
- 若回归只是确认"别再出运行时错误"，仿真测试也能用。
> 所以正确表述是：**"回归测试是一种目的，基线测试是它最常用的手段"，二者是"目的—手段"关系，不是并列关系。** 官方教程 `gs/create-a-simple-baseline-test.html` 开头原话："当您更改模型并希望确保输出与基线数据匹配时，可以在**回归测试**中使用**基线测试**。"——正好印证这一点。
